Dodo Payments · Console design · v4 — as built

Merchant Risk Console

The console is running. This is what shipped, and — more usefully — the four places where the design we wanted and the data we actually have disagreed, and what we did about it. Every number on every screen is computed by the engine. Nothing here is a placeholder.

1The shell

A fixed left sidebar with eight destinations, a global search, and a status card that reports what the memory layer currently believes. The palette is Dodo’s own: lime #C6FE1E on the active item and the primary action, forest-green-black #00160D for text.

Two things are deliberately absent. The always-on summary bar from v3 is gone — once an Overview screen existed, a strip repeating the same five numbers on every tab was duplication, and it made Chat and History harder to read for no gain. And there are no Reports, Integrations or Settings tabs: we had nothing real to put behind them, and an empty destination is worse than a missing one.

3Where the design and the data disagreed

The design we worked from asked for four things the engine cannot honestly produce. Each was substituted rather than faked, because a demo that prints a confident number it cannot derive is the exact failure this project exists to prevent.

Asked forShippedWhy
Memory accuracy 94.6%Memory confidence 90.6%There is no accuracy metric. Mean confidence across the records currently in force is a real quantity the store can report.
↑12% vs last monthDeltas computed from decision datesTwo of the four stats have no prior period to compare against. They carry a note instead of an invented arrow — which is why one reads −8%, not a flattering ↑.
Memory score /100 per merchant100 − P(bad), labelled as suchA bare score invites the reader to think it means something independent. It is one number in two dresses, and the column says so.
Retail, F&B, Electronics, ApparelDodo’s policy categoriesSaaS, AI product, digital goods, templates & plugins, ebooks. Generic retail verticals describe a business Dodo is not in.
The rule that produced all four

Every figure on screen is traceable to something the engine computed. Where the data does not support the design, the design changes — not the number.

4Merchants and the graph

Merchants is the full corpus, searchable and filterable by risk band, sorted by P(bad) descending so the merchants that can move sit at the top. A merchant that has not started transacting reads “not live”, not $0.

Graph explorer draws the corroborating routes between an applicant and merchants we have already judged. Shared entities above degree 40 are treated as hubs and never carry corroboration — a shared payment processor is not evidence. That suppression is what keeps the graph from asserting that half the portfolio is related to the other half.

5Two bugs the build surfaced

Seeding the corpus with Dodo’s real, publicly-named customers is a test as much as a feature: a clean population that the engine must clear. It did not, twice — and both failures were the same mistake wearing different clothes. Prose similarity being mistaken for evidence.

SymptomCauseFix
A clean merchant pushed to 22%A memory reading “refund rates above 15 percent…” carried no predicate, so it matched on text. Any pitch containing “subscription” and “free trial” fired it.The memory now carries the predicate its own prose names: refund_rate ≥ 0.15. Behavioural lessons match on the observable, never on the wording.
A clean merchant drawing a 3× likelihood ratioPrecedent search had no similarity floor. A neighbour matching at cosine 0.13 on subscription, saas, github, email counted as precedent.A measured floor of 0.20. Genuine precedent in this corpus sits at 0.24 and above; below that the shared vocabulary is the corpus’s, not the merchant’s.

Both carry regression tests. The floor is documented with the measurement that produced it, not asserted as a constant.

6Real Dodo merchants in the corpus

All 17 publicly-named Dodo customers are seeded: Mole, Vibe3D, Draftly, ReplyDaddy, CatDoes, Indilingo, Scira AI, PeerPush, IndieKit, Betide Studio, Healthify, Parakeet AI, MATIKS, GPAI, Cardboard, SurgeGrowth and Vaya. They give the demo a control population with real product descriptions and plausible operating shapes, against ~4,000 invented merchants.

Hard rule, enforced in code

A real merchant never appears next to an adverse finding. Not flagged, not declined, not in a fraud ring, not graph-linked to a terminated merchant, never carrying a “went bad” label, never cited as adverse precedent.

These are real businesses. A screenshot showing one two hops from a piracy termination would be defamatory in effect regardless of intent. The corpus is randomised, so this is an assertion in build() plus six tests that fail the build — not a convention. Every fraud ring and every termination uses an invented name.

Product descriptions are factual, drawn from public sources. Operating figures — volume, transaction counts, refund rates — are illustrative, and the interface says so.

7Where Claude goes — and where it must not

Claude doesClaude never
Compose the answer from retrieved contextDecide. The P(bad) arithmetic stays deterministic
Read an unstructured application into fieldsInvent evidence not present in the retrieval
Draft a candidate memory from a rationaleWrite to memory silently — reconciliation is explicit
Suggest a distilled pattern after an incidentPromote a pattern past the replay gate

The gate is the load-bearing part: a distilled pattern is promoted only if, replayed over the whole corpus, it catches more without flagging more. That delta is the anti-fragility claim expressed as a number rather than an adjective.

The API key

The key lives in an environment variable on the server. The browser calls our endpoint; our server calls Anthropic. A key in client-side code is readable through view-source and billable by whoever finds it. The console degrades to the deterministic path when no key is set — every screen above renders either way.
